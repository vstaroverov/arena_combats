# ЮKassa: платный баланс

## Текущий статус

Интеграция добавлена в версии 2.3.0; в 2.3.1 добавлен режим тестирования без чеков. Приём денег по умолчанию **выключен**. Для тестового магазина 1509255 проверены авторизация в API и создание платежа на 100 ₽ со статусом pending и test=true. Оплата этого заказа и доставка webhook не выполнялись. Реальные деньги не списывались. Автоматические проверки используют имитацию API. Установка тестового магазина на arena.v-star-group.ru описана в TEST_DEPLOYMENT.md; секрет в сборку не включён.

Есть два независимых баланса:

- **Бесплатные игровые очки**: стартовые 15 000, бесплатное пополнение, пари и игровые выигрыши. Не продаются, не обмениваются на платные единицы и не выводятся.
- **Платный баланс**: пополнение через ЮKassa, 1 ₽ = 1 единица. Только поддержка бойцов и создание бойца, без участия в пари и без игровых денежных выигрышей.

Старый игровой баланс не превращается в купленные средства. Новый платный баланс начинается с нуля. Уже созданные бойцы и результаты сохраняются. Снимок мира мигрирует со схемы 2 на схему 3 одной транзакцией; старые выпуски откажутся открывать новую схему. Тестовые платежи хранятся на отдельном техническом балансе и не дают боевых средств; для тестирования магазина использовать отдельную базу/адрес.

## Переменные окружения

`PUBLIC_ORIGIN` — настоящий HTTPS-домен без пути. Секрет задаётся только в окружении сервера или в локальном `.env`, который исключён из Git. Не вставлять его в HTML, JavaScript браузера, чат, команды с выводом в логи или репозиторий.

| Переменная | Значение |
| --- | --- |
| `YOOKASSA_ENABLED` | `1` для включения; по умолчанию `0` |
| `YOOKASSA_MODE` | `test` или `live`, должен соответствовать магазину/ключу |
| `YOOKASSA_SHOP_ID` | Идентификатор подключённого магазина |
| `YOOKASSA_SECRET_KEY` | Секретный API-ключ этого магазина |
| `YOOKASSA_RECEIPT_MODE` | `payment` — данные чека в платеже; `external` — независимая фискализация продавца; `test_no_receipt` — только тестовый магазин без чеков |
| `YOOKASSA_VAT_CODE` | Код НДС магазина, без автоматического выбора |
| `YOOKASSA_PAYMENT_SUBJECT` | Подтверждённый предмет расчёта: `service`, `intellectual_activity` или `payment` |
| `YOOKASSA_PAYMENT_MODE` | Встроенный сценарий поддерживает `full_payment` |
| `YOOKASSA_TAX_SYSTEM_CODE` | При необходимости код системы налогообложения 1–6 |
| `YOOKASSA_EXTERNAL_RECEIPTS_CONFIRMED` | `1` только при реально настроенной независимой фискализации |

Настройки чеков нужно подтвердить для своей организации и модели продажи виртуальных единиц. Встроенный сценарий передаёт email и чек полного расчёта с платежом. Схема аванса с последующими отдельными чеками при каждом расходовании здесь не реализована: если для магазина нужна именно она, сначала требуется доработка фискализации. Режим `external` не создаёт чеки сам и не означает освобождения от обязанностей продавца.

Значения параметров и актуальные ставки опубликованы в [справочнике ЮKassa для чеков](https://yookassa.ru/developers/payment-acceptance/receipts/54fz/yoomoney/parameters-values). Не копировать налоговые значения из тестовых фикстур.

Обычный `npm start` не читает `.env`. Использовать `node --env-file=.env server.mjs` или переменные окружения хостинга. Dockerfile включает платёжный модуль; секрет передаётся при запуске контейнера, не в образе.

Для проверки без фискальных параметров разрешено сочетание `YOOKASSA_MODE=test` и `YOOKASSA_RECEIPT_MODE=test_no_receipt`. В боевом режиме такая конфигурация отключает оплату. В тестовом кабинете при этом не должен быть включён режим обязательной проверки чеков. Проверка чеков — отдельный этап по [инструкции ЮKassa](https://yookassa.ru/developers/payment-acceptance/testing-and-going-live/testing#receipts).

## HTTP-уведомления

В личном кабинете нужного магазина настроить адрес:

```text
https://ВАШ-ДОМЕН/api/payments/webhook
```

Подписаться на `payment.succeeded`, `payment.canceled`, `refund.succeeded`. Внешний HTTPS-порт — 443 или 8443. Reverse proxy должен передавать POST и JSON на Node без кэширования, авторизационного редиректа и проверки браузерного Origin для этого адреса.

Секретной подписи webhook в этой интеграции нет: сервер сам запрашивает платёж в API ЮKassa с ключом магазина и проверяет сумму, RUB, metadata заказа/профиля, получателя, test/live, статус succeeded и paid. Полям входящего уведомления и параметрам возврата в URL зачисление не доверяет. Это соответствует [проверке актуального статуса объекта из документации ЮKassa](https://yookassa.ru/developers/using-api/webhooks).

## Создание и подтверждение

Пользователь открывает «+» у платного баланса, выбирает целую сумму от 100 до 50 000 ₽ и при необходимости email для чека. Карта вводится на странице ЮKassa, реквизиты карты приложение не получает. Перед оплатой нужно сохранить свой GUID.

Заказ и параметры сохраняются до API-запроса. В API используется UUID заказа как Idempotence-Key. Повтор в браузере, сетевой сбой и перезапуск используют тот же заказ. Автоматическое зачисление происходит после проверенного succeeded, независимо от возвращения покупателя в браузер. Незавершённые известные заказы дополнительно сверяются раз в минуту.

Гарантия идемпотентности API ограничена 24 часами. Приложение перестаёт пересоздавать неизвестный платёж через 23 часа и помечает заказ needs_review. Это требует проверки в кабинете магазина вместо нового списания. Основа — [формат взаимодействия и идемпотентность ЮKassa](https://yookassa.ru/developers/using-api/interaction-format).

Не больше пяти новых заказов на профиль в час. Клиент повторно использует requestId для той же суммы; другая сумма создаёт другой запрос. Кнопка проверки статуса доступна в истории последних пополнений. Секреты, email, полное тело запроса и чужие платежи в эту историю не выдаются.

## Платёжный учёт, возвраты и хранение

Таблицы `payment_orders`, `paid_ledger`, `paid_actions` — отдельный платёжный учёт в той же SQLite-базе. Зачисление и изменение кошелька сохраняются одной транзакцией. Оплаченные поддержки/создание защищены долговременной уникальной квитанцией, даже после обычной очистки игровых квитанций.

Уведомление refund.succeeded проверяется через актуальный платёж и его накопленную сумму возврата. Возврат уменьшает платный баланс один раз. Если единицы уже потрачены, баланс может стать отрицательным; новые платные покупки будут недоступны до покрытия разницы. Прошлые бои, поддержка и созданные бойцы автоматически не откатываются. Само оформление возврата выполняет продавец в ЮKassa; публичного API вывода денег в игре нет.

Данные чеков/email в теле успешно завершённых и отменённых заказов убираются через 30 дней. Минимальные финансовые записи и защита от повторного списания не удаляются ежедневной очисткой игровых логов. Сроки дальнейшего финансового архива должен определить продавец. Тестовый и реальный платёжный учёт различаются и не объединяются.

## Запуск и обновления

1. Настроить тестовый магазин на отдельном адресе и отдельной SQLite-базе, согласовать модель чеков и параметры.
2. Подключить события webhook. Проверить успех, отмену, повторное уведомление, возврат и восстановление после перезапуска с тестовыми ключами.
3. Подключить боевой магазин, HTTPS-домен, реальные ключи и подтверждённые настройки фискализации. Опубликовать условия покупки, сведения продавца и контакт для возвратов на своём сайте.
4. После проверки владельцем включить live. Самостоятельная реальная покупка для проверки разработчиком в этой задаче не выполнялась.

После включения реальных платежей **нельзя откатывать базу к старой копии как обычное игровое сохранение**: можно потерять сведения о принятых оплатах. При обновлении сохранять актуальную базу и совместимость схемы. Для аварийного восстановления нужны сверка с реестром ЮKassa и восстановление пропущенных заказов/кошельков, а не повторное создание платежей.

Если заказ needs_review найден в кабинете ЮKassa по metadata.order_id, можно повторно доставить настоящее уведомление с его provider payment ID на webhook: сервер перепроверит API и сможет связать его с сохранённым заказом. Если локальный заказ утрачен, уведомление не подтверждается успехом — требуется восстановление данных и ручная сверка. Нельзя вручную проставлять credited_minor без записи кошелька/учёта одной транзакцией.
