# ЯРОСТЬ 2.3 — единый мир, GUID и ЮKassa

## Требования

- Node.js 24+ и постоянно работающий процесс. Зависимости npm устанавливать не нужно.
- Постоянный диск для SQLite. По умолчанию база — `data/world.sqlite` рядом с сервером.
- Один экземпляр приложения на базу мира. Не включать несколько workers, кластер или независимые реплики: для горизонтального масштабирования потребуется отдельная архитектура симуляции и хранилища.
- HTTPS-домен и reverse proxy на Node-сервер. Проксировать весь сайт, включая `/api/state`, `/api/action`, `/api/presence` и `/api/health`. Не кэшировать `/api/`, не менять методы запросов и передавать cookie.

Папки `dist/` без сервера недостаточно. При недоступности API интерфейс переподключается, отдельный локальный мир не создаётся.

## Локальный запуск

```sh
npm start
```

Открыть http://127.0.0.1:4173. База создаётся автоматически. Бои идут даже без открытого браузера.

## VPS / Node-хостинг

Загрузить исходники из репозитория и задать переменные окружения:

```sh
HOST=127.0.0.1 PORT=3000 PUBLIC_ORIGIN=https://game.example.com WORLD_DB=/var/lib/yarost/world.sqlite TRUST_PROXY=1 node server.mjs
```

Подставить настоящий домен. Каталог базы должен существовать или его создание должно быть разрешено пользователю процесса. Использовать менеджер процессов с автоматическим перезапуском и одним worker. Базу хранить за пределами папок заменяемых выпусков.

В PowerShell:

```powershell
$env:HOST = '127.0.0.1'
$env:PORT = '3000'
$env:PUBLIC_ORIGIN = 'https://game.example.com'
$env:WORLD_DB = 'C:/yarost-data/world.sqlite'
$env:TRUST_PROXY = '1'
node server.mjs
```

Можно скопировать `.env.example` в `.env`, исправить значения и выполнить `node --env-file=.env server.mjs`. Обычный `npm start` сам `.env` не загружает. Для контейнера или хостинга, ожидающего внешний bind, использовать `HOST=0.0.0.0`.

`PUBLIC_ORIGIN` должен совпадать с HTTPS-адресом сайта: он участвует в проверке POST-запросов, а сессионная cookie при HTTPS получает флаг Secure. Внешний HTTPS проксируется к внутреннему HTTP-порту Node.

## Docker

```sh
docker build -t yarost:2.3.2 .
docker volume create yarost-data
docker run -d --name yarost --restart unless-stopped -p 127.0.0.1:3000:3000 -e PUBLIC_ORIGIN=https://game.example.com -e TRUST_PROXY=1 -v yarost-data:/app/data yarost:2.3.2
```

Повторно использовать **тот же volume** при замене контейнера. Без постоянного тома удаление контейнера может привести к потере мира. Образ в текущей среде не собирался.

## GUID, сессии и блокировки

Новый браузер получает отдельный профиль и случайный UUID v4 как секретный GUID-код входа. Меню «Мой GUID / Войти» позволяет скопировать код, отметить его сохранение и войти по ранее сохранённому коду. Код даёт полный доступ к личному профилю; не публиковать его и не записывать в логи аналитики. Он выдаётся только авторизованному владельцу через `/api/account` с `Cache-Control: no-store`, в общем состоянии мира кодов нет.

Cookie `yarost_session` — независимый случайный токен, HttpOnly, SameSite=Strict; срок один год. При входе по GUID сессия меняется; существующие сессии других устройств продолжают работать. Балансы профилей не объединяются. Без cookie и GUID восстановление не предусмотрено. GUID и сессии хранятся в той же приватной SQLite-базе и входят в резервную копию.

Ошибка при вводе GUID блокирует только вход по коду на 24 часа для текущего браузера и IP. Блокировка переживает перезапуск, действует после очистки cookie и не продлевается от заблокированных повторных запросов. Просмотр арены и действия из уже открытого профиля доступны. На общей сети блок затрагивает вход по коду с того же IP; сам целевой профиль с других IP не блокируется.

По умолчанию `TRUST_PROXY=0`: IP берётся из TCP-соединения, произвольный X-Forwarded-For игнорируется. **За одним доверенным reverse proxy установить `TRUST_PROXY=1`**, чтобы блокировался адрес посетителя, а не общий адрес прокси. Прокси должен перезаписывать X-Forwarded-For реальным клиентским IP или добавлять его последним; Node-порт закрыть от прямого внешнего доступа. Не включать этот режим, если посетители могут напрямую отправлять запросы на Node-порт. При нескольких прокси требуется отдельная настройка определения адреса.

При обновлении с 2.0 существующие гостевые кошельки получают GUID автоматически, сохраняя старые cookie, владение бойцами и баланс. Таблицы авторизации создаются в текущей базе без сброса мира. Сначала сделать резервную копию.

Версия 1 хранила независимые миры в localStorage. Их автоматического объединения нет; старая запись `combat-demo-v1` не удаляется. Первый запуск версии 2 создаёт новый общий мир. С версии 2.3 есть отдельная интеграция ЮKassa, выключенная до настройки магазина/домена/чеков; бесплатные пари не используют платный баланс. Вывода средств из игры нет. Настройка — PAYMENTS.md.

## Резервные копии и обновления

Сервер сам удаляет временные данные при запуске и после московской полуночи; полный перечень сроков — в RETENTION.md. В версии 2.2 таблицы сессий получают сроки истечения без сброса действующих cookie. В runtime обязательны также retention.mjs и maintenance.mjs. Новые таблицы и поля создаются автоматически в прежней базе, перед обновлением сделать backup.

База освобождает и переиспользует страницы, при необходимости выполняет VACUUM. Для большого файла предусмотреть свободное место и возможную задержку обслуживания во время уплотнения. Копии базы и логи внешнего reverse proxy/менеджера процессов нужно ротировать средствами хостинга: автоматическая очистка игры их не затрагивает.

Сделать согласованную копию работающей базы (учитывает SQLite WAL):

```sh
npm run backup
```

Если задан внешний `WORLD_DB`, он должен быть задан и при запуске команды backup. Путь назначения можно передать аргументом: `npm run backup -- /safe/path/world-before-update.sqlite`. В Docker: `docker exec yarost node scripts/backup.mjs /app/data/backup-before-update.sqlite`, затем скопировать файл наружу командой `docker cp yarost:/app/data/backup-before-update.sqlite ./backup-before-update.sqlite`.

Не копировать один `world.sqlite` из работающего сервера: свежие записи могут находиться в `world.sqlite-wal`. Хранить резервные копии отдельно от контейнера и Git.

Порядок обновления:

1. Проверить новый выпуск на отдельной копии базы и другом адресе. Не подключать тестовый экземпляр к рабочему файлу.
2. Запустить `npm test`, сделать backup и сохранить предыдущий код/образ.
3. Остановить старый процесс, заменить код и запустить один новый процесс с прежним `WORLD_DB` и доменом.
4. Проверить `/api/health` (`ok: true`, после восстановления `catchingUp: false`), бой и две независимые сессии. Сервер догоняет время простоя небольшими пакетами, поэтому после долгого отключения синхронизация занимает время.
5. При несовместимом изменении схемы использовать миграцию выпуска. Сервер откажется открывать неизвестную версию схемы вместо сброса мира.

Откат: остановить процесс, сохранить проблемную базу со всеми сопутствующими файлами в отдельном каталоге, вернуть предыдущий код и **соответствующую ему резервную копию**. Запустить с файлом копии как `WORLD_DB`, без старых WAL/SHM под тем же именем. Откат базы отменяет действия после момента копии — это нужно учитывать при выборе точки восстановления.

**После включения реальных платежей этот способ отката базы без сверки недопустим:** он может удалить сведения об оплаченных заказах. Сохранять актуальную платёжную базу, применять совместимые миграции и при аварии сверяться с реестром ЮKassa. Текущий выпуск оставляет реальные платежи выключенными. Подробный порядок подключения и восстановления — PAYMENTS.md. В runtime обязателен payments.mjs; проксировать также /api/payments, /api/payments/*/check и /api/payments/webhook.

Статика выдаётся с `Cache-Control: no-cache`, API — с `no-store`. CDN должен соблюдать эти заголовки. Клиент не изменяет локально баланс и не рассчитывает результаты; при потере сети показывает состояние соединения и переподключается.

## SEO и проверка после установки

В `dist/index.html` уже есть title, description, Open Graph, Twitter, VideoGame JSON-LD (MultiPlayer), один H1 и фавиконы. После выбора домена добавить canonical, og:url, абсолютные URL изображений и sitemap.xml. Семантическое ядро — `SEO_CORE.md`.

Проверить главную, иконки, создание бойца, поддержку, лайки, ставки, две независимые сессии и перезапуск с сохранением базы. Счётчики зрителей живут в памяти и при перезапуске набираются заново.
